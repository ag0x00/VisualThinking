# Live Coding and Algorave

A framing within [[Framings of Generative Art|generative art]] in which the *act of writing code in performance, in front of an audience*, is the artwork. The framing's institutional anchor is **TOPLAP** (Temporary Organisation for the Promotion of Live Algorithm Programming), founded in February 2004 in a Hamburg bar by Alex McLean, Nick Collins, Julian Rohrhuber, and others. The matching musical-cultural form is **algorave**: live electronic dance music generated in real-time through live-coded algorithms. McLean registered algorave.com in 2012 as the cultural-form name.¹

> [!note] This is one of nine framings in [[Framings of Generative Art]]
> Live-coding's core claim — *the code is the score and the performance* — contests every framing that treats code as instrumental. Showing the code is mandatory ("Show us your screens"). The visual aesthetic is often secondary to the *performativity*.

## Essence

The TOPLAP manifesto's central injunctions:
- "Give us access to the performer's mind, to the whole human instrument."
- "Obscurantism is dangerous. Show us your screens."
- "Algorithms are thoughts. Chainsaws are tools. That's why algorithms are sometimes harder to notice than chainsaws."¹

The framing insists that code is not infrastructure for an artwork — it *is* the artwork. The projected editor showing the live-modified code is the visual core of the performance. Audiences watch the artist think.

Algorave extended this into electronic-dance-music performance: the music *and visuals* are generated by code being live-edited on stage, with audience members dancing to it. Sheffield (UK) is often credited as the algorave birthplace.²

## Key practitioners and key tools

- **Alex McLean** — *TidalCycles* (Haskell-embedded pattern DSL). Manifesto co-author. Algorave organizer.³
- **Sam Aaron** — *Sonic Pi* (Ruby-based; pedagogical reach in UK schools).
- **Andrew Sorensen** — *Extempore*; performances of *live-coded music for piano* with live-edited algorithmic accompaniment.
- **Olivia Jack** — *Hydra* (live-coded visual synthesis in the browser). This is also one of the wiki's evaluated [[Hydra|tools]] and is arguably the most direct path from live-coding theory to music-reactive visuals.
- **Renick Bell, Joana Chicau, Iván Paz, Niklas Reppel** — contemporary algorave performers.
- **Charlie Roberts** — *Gibber* (browser-based live-coding).

## What it foregrounds that other framings don't

- **Performance.** Code-as-score-and-instrument. Music conservatories teach "performance practice"; live-coding is its computational analog.
- **Transparency.** Code on screen, mutable in front of audience. "Show us your screens" is a manifesto principle.
- **Real-time process.** Compilation/evaluation happens during the performance. Hot-swap of running code is core.
- **Improvisation.** Like jazz — improvisation over a structure (functions, samples, rhythmic primitives).
- **Pedagogy and openness.** TOPLAP, TidalCycles, Sonic Pi, and Hydra are radically open about their tooling; the framing has high pedagogical and DIY culture.

## What it contests

- **Studio-research:** practice-led work is private, iterative, slow. Live-coding is public, performative, fast.
- **Long-form on-chain:** on-chain is deterministic and persistent; live-coding is ephemeral and improvised. Diametric values.
- **AI-art / latent-space:** the model is opaque, the generation hidden. Live-coding insists the *opposite*: transparency, code legibility, audience access to the mind of the performer.
- **Galanter:** Galanter's autonomy framing fits poorly — live-coding *minimizes* autonomy because the human is constantly editing the running system.

## Computable handles

- **DSL design.** TidalCycles is the canonical example: Haskell-embedded combinators for cyclic patterns. The DSL is the artist's instrument. *Most* live-coding tools require a custom DSL.
- **Hot-swap evaluation.** AST-level replacement of running functions; rebinding live audio buses; eval-loops in browser-based tools.
- **Audio reactivity.** Audio analysis (FFT, onset detection, peak tracking) drives visual parameters. See [[Web Audio API and AudioWorklet]] for the browser-based pipeline.
- **Visual pattern DSLs.** [[Hydra]]'s shader-composition syntax: `osc(60,0.1,1.5).kaleid(4).out()` — the entire program fits in one tweet, and produces dense visuals.
- **WebGPU live-coding** (emerging). [[q5.js]] and direct WebGPU shaders enable browser-native live-coded visuals at frame rates impossible with WebGL+JS.

## Fit with the four user priorities

- **1. Generative art (medium).** The performative framing limits static-output applicability, but the visual style and tooling transfer to non-performance generative art.
- **2. Branding (low).** Performance ≠ identity-system. Some overlap in algorave / NTS / underground music branding which adopts live-coding aesthetics.
- **3. Graphic design (low).** Static deliverables don't capture the framing's core.
- **4. Music-reactive (high — the canonical framing).** This is the wiki's strongest argument for live-coding: priority 4 (Apple Music Visualizer–style music-reactive visuals) is *exactly* what TOPLAP / Hydra / algorave do, except in performance contexts rather than studio renderings.

## Programmability handle

For the user's music-reactive priority specifically:
- **Adopt Hydra-style composition.** [[Hydra]]'s functional-composition vocabulary (oscillator → kaleidoscope → distortion → output) is small enough that an LLM can generate and modify Hydra programs reliably. This is the easiest path to *LLM-driven music-reactive visuals*.
- **Use Web Audio API + AudioWorklet** for the audio side. Onset detection, peak tracking, and FFT bin extraction translate audio to numeric streams the LLM can map to visual parameters.
- **Verify Michotte's 70 ms causality threshold.** Per Arnheim Sweep 3, perceived causality between audio events and visual responses requires <70ms latency. AudioWorklet → WebGPU pipelines can achieve this; setTimeout-driven loops cannot.
- **Live-coding tools are *also* studio tools.** Hydra is usable for offline rendering; sketches can be exported. This makes the framing's tools relevant beyond the performance context.

## Critique

- Algorave culture has been criticized as a niche scene with limited mainstream traction; the manifesto's transparency principle is partly aesthetic-political branding more than artistic necessity.
- The DSL-design problem is hard. Most live-coding systems involve very steep learning curves. Hydra is unusually approachable; TidalCycles is unusually opaque.
- The framing's purism about transparency conflicts with practical needs (pre-recorded samples, prepared scaffolding, layered abstraction). In practice, most algorave sets are partly *prepared*, with live-editing on top.
