# q5.js

A **WebGPU-powered alternative to [[p5.js]]** by **quinton (qashto)** (2022+). Marketed as a **drop-in replacement** for p5.js with much higher performance via WebGPU. Has its own physics-engine sibling (q5play) and is the underlying engine for a growing set of derived libraries.

**Verdict: first-class emerging library — watch closely.** Worth serious consideration for new priority-1 / priority-4 work when p5.js performance is the bottleneck and you want the p5.js mental model with WebGPU speed.

## Purpose (one line)

p5.js-compatible-API creative-coding library powered by WebGPU, optimized for performance-intensive interactive art and game engines.

## Why this wasn't in the original Tools sweep

This is an honest miss. The original sweep evaluated p5.js but didn't survey the wider sibling-library landscape; q5.js as a separate (not-a-plugin) library was outside the catalog stub's stated scope. Surfaced by an npm-survey audit 2026-05-17.

### Paradigm coverage

Same as p5.js (rule-based, stochastic, iterative, learning-based via integrations) — but **with significantly better performance ceiling** because of the WebGPU backend.

The notable upgrade for the **iterative / dynamical-systems** paradigm: q5.js makes shader-based CA, RD, particle systems much more accessible than p5.js's WEBGL mode.

### Idiomaticity and LLM-codegen friendliness

**Score: 3 / 5** (provisional) — growing rapidly:

- **API mirrors p5.js** intentionally, so p5.js training data partially transfers. LLM-generated p5.js code often runs unmodified on q5.js.
- **Smaller direct training-data presence** than p5.js — newer library; community building.
- **Active documentation** at https://q5js.org/.

This is the main caveat: q5.js is **young**. LLM codegen reliability will improve substantially over the next year as adoption grows.

### Production-readiness

**Score: 3 / 5** (provisional) — promising but young:

- Released 2022+; active development with multiple releases per week.
- LGPL-3.0 licensed (copyleft, note for commercial use).
- 3,462 weekly npm downloads (small but growing fast).
- Production usage: q5play game engine (sibling project, 862 weekly dl).
- The single-maintainer status (qashto) is the main risk for sustained adoption.

### What's actually different from p5.js

The marketing claim is "p5.js-compatible-but-faster," but there are genuine architectural differences:

| Feature | p5.js | q5.js |
|---|---|---|
| Default backend | Canvas2D | **WebGPU** (with Canvas2D + WebGL fallback) |
| Performance ceiling | ~5k primitives at 60fps | **100k+ primitives** (WebGPU compute) |
| API surface | ~200 functions | Mostly compatible; subset + extensions |
| WEBGL mode | Yes (legacy) | Native WebGPU (no separate mode) |
| Bundle size | ~250kB gzipped (full) | ~150kB gzipped (more modular) |
| Shader access | GLSL via WEBGL mode | WGSL via WebGPU |
| Sister projects | p5.sound, p5.play, etc. | q5play (Box2D physics) |

For priorities where performance matters (priority 4 visualizers especially), q5.js's WebGPU backing is a substantial advantage.

## Use-cases q5.js excels at

- **Dense, high-particle-count generative art** at p5.js-like ease-of-use.
- **Music-reactive visualizers** that need WebGPU performance but want the p5.js mental model.
- **GPU-accelerated CA / RD / particle systems** without the WebGPU boilerplate.
- **New projects** that can target modern browsers (WebGPU support required).

## Use-cases q5.js is wrong for

- **Maximum-compatibility browser support** (legacy / older browsers without WebGPU): use p5.js.
- **Heavy reliance on the p5.js plugin galaxy** (p5.sound, p5.brush, etc.): plugin compatibility is partial, evolving.
- **Pedagogical context where students will be looking up p5.js answers**: stay on p5.js for the documentation continuity.
- **Production codebases that need very stable APIs**: q5.js is too young; major versions ship rapidly.

## How to think about the q5.js / p5.js choice

- **For new priority-4 (music visualizer) work**: lean toward q5.js — performance ceiling matters; you'll appreciate the WebGPU backing.
- **For new priority-1 (generative art) static work**: either; p5.js for ecosystem, q5.js for performance.
- **For new pedagogical / prototype work**: p5.js, for the unmatched documentation and community.
- **For existing p5.js codebases**: stay on p5.js; the migration path is open but not free.
- **For "I want WebGPU but with creative-coding ergonomics"**: q5.js is exactly this proposition.

## Connection to the wiki's framework

q5.js sits **between** [[p5.js]] (familiar API) and [[WebGPU]] (raw performance). For the wiki's recommended priority-4 stack (Web Audio API → visualizer → WebGPU rendering), q5.js is a **simpler entry point** than learning raw WebGPU + WGSL while keeping most of the performance benefit. It's worth considering as a substitute for the **three.js + WebGPU** combination when 3D isn't needed and the p5.js-style imperative API fits.

## Caveats

- **Younger ecosystem** — fewer tutorials, smaller community, less LLM training data than p5.js.
- **WebGPU browser support** is the constraint — needs Chrome / Edge 113+ or recent Safari / Firefox.
- **Plugin compatibility** with the p5.js addon galaxy (p5.brush, p5.sound, p5.play, etc.) is partial. p5play has been ported to q5play; other plugins are case-by-case.
- **LGPL-3.0 license** (copyleft) — note for commercial use. Different from p5.js's permissive license.
- **Single-maintainer risk** — qashto is the sole active maintainer; sustainability depends on their continued work or community uptake.
