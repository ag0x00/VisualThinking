# p5.js

The **JavaScript port of Processing** (Lauren McCarthy 2014+). Designed for **accessibility, inclusivity, and a low-friction creative-coding entry point**. Runs in the browser via HTML5 canvas; no build step required.

**Verdict: first-class for pedagogy and prototyping; second-class for production work** that requires high performance, advanced 3D, or strict typing.

## Purpose (one line)

Beginner-friendly creative-coding library with a Processing-inherited API for 2D drawing, image manipulation, and basic 3D, running in the browser.

## Rubric scores

### Purpose-fit per priority

| Priority | Score | Why |
|---|---|---|
| 1. Generative art (static + dynamic) | **4 / 5** | Strong for static-canvas generative art; performance limits for dense dynamic work |
| 2. Branding | **3 / 5** | Can do parametric mark generation; SVG export is shaky; vector-first work is better in paper.js |
| 3. Graphic design | **3 / 5** | OK for posters / hero compositions; weak for typography-heavy work |
| 4. Music-reactive visualizers | **3 / 5** | p5.sound is built-in but limited; modern audio work prefers raw Web Audio API + WebGPU |

### Paradigm coverage

- ✅ **Rule-based / deterministic**: drawing primitives, deterministic state, very natural.
- ✅ **Stochastic / random-within-rules**: built-in `random()`, `noise()` (Perlin); seedable via `randomSeed()`, `noiseSeed()`.
- ✅ **Iterative / dynamical-systems**: `draw()` loop is natural for CA, particles, RD. WEBGL mode for shader access.
- ⚠️ **Evolutionary**: no built-in support; bring your own GA. Possible but not idiomatic.
- ⚠️ **Learning-based**: ml5.js is a sibling library (same team) that adds this. Together p5.js + ml5.js cover the paradigm.

### Autonomy-control fit

**Score: 3 / 5** — most natural in the middle of the gradient (parametric / stochastic-rule). Fully-controlled work feels over-imperative; fully-autonomous live-coding is better done in Hydra.

### Primitive vocabulary

- ✅ 2D primitives: shapes (`rect`, `ellipse`, `triangle`), paths (`beginShape`, `vertex`, `endShape`), text.
- ⚠️ 3D primitives: WEBGL mode adds basic 3D (`box`, `sphere`, `model`), but it's clunky compared to three.js.
- ⚠️ Color: only RGB / HSB out of the box. **No OKLCH or Lab**. Have to bring chroma.js / culori.
- ✅ Noise: built-in Perlin (`noise()`); no simplex out of the box.
- ⚠️ Composition primitives: none; you write your own grids, golden-section helpers, etc.
- ⚠️ Pattern primitives: no GPU instancing; performance falls off for >5k primitives at 60 fps.

### Idiomaticity and LLM-codegen friendliness

**Score: 5 / 5** — among the most-LLM-friendly libraries because:

- **Massive training-data presence** (Processing + p5.js code is everywhere — pedagogy, art portfolios, Genuary archives, Stack Overflow).
- **Consistent API conventions** (function-first, global state, predictable naming).
- **Excellent documentation** with examples for almost every function.
- **Tight, predictable API surface** (~200 commonly-used functions vs three.js's thousands).
- **Errors are catchable in `setup()` / `draw()`** and the patterns are well-known.

The downside: p5.js is **untyped by default**. TypeScript definitions exist (`@types/p5`) but are best-effort. For typed work, you'll lose some LLM-codegen quality.

### Production-readiness

**Score: 4 / 5** — active, well-maintained, MIT-flavored license (LGPL-2.1, mostly-permissive for end-product use), bundle size moderate (~250kB gzipped for full library). The Processing Foundation provides organizational continuity. Performance ceiling is the main caveat — p5.js draws via Canvas2D (default) or WebGL (in WEBGL mode); both are slower than custom WebGPU pipelines.

## Compared to direct alternatives

| Alternative | When to prefer it |
|---|---|
| **Processing (Java)** | Native performance; classroom use with Processing's IDE. Otherwise p5.js is better. |
| **paper.js** | Vector-graphics-native, SVG export, hit-detection on shapes. |
| **three.js** | Anything 3D. p5.js's WEBGL mode is no contest. |
| **Two.js / Pixi.js** | Pure 2D where performance matters. Pixi specifically for high-density particle work. |
| **Hydra** | Real-time music-reactive live-coding. Hydra is purpose-built for this. |

## Use-cases p5.js excels at

- **Teaching**: the API and documentation are designed for accessibility. Use p5.js when the audience includes beginners.
- **Prototyping**: get an idea on screen in 10 lines.
- **Genuary-style daily generative**: simple primitives, low overhead, rapid iteration.
- **Art-portfolio sketches**: most generative-art portfolios are p5.js sketches.
- **LLM-generated quick demos**: the LLM-codegen friendliness compounds with the rapid iteration.

## Use-cases p5.js is wrong for

- **High-performance real-time work** (priority 4 visualizers with thousands of particles): use WebGPU or three.js with InstancedMesh.
- **3D-heavy generative art** (volumetric, advanced shaders, GLTF model rendering): three.js native is much better.
- **Vector-output for print / brand work** (priority 2): paper.js's vector model is purpose-built.
- **TypeScript-strict production codebases**: the typing is best-effort, not a first-class language target.

## Connection to the wiki's framework

p5.js sits in the **middle of the autonomy-control gradient** (parametric → stochastic-rule paradigms). It's the **canonical entry point** to the [[Algorithmic Art History|Reas-Fry creative-coding lineage]]. The wiki's many references to "generative art" implicitly assume a p5.js-like API.

For complete pipelines targeting the wiki's priorities, p5.js is typically **the prototype substrate**, with production work migrating to three.js / WebGPU as performance and 3D requirements grow.

## Plugin ecosystem and sibling libraries

See **[[p5.js Plugin Ecosystem]]** for the substantive p5.* plugins (p5.brush, p5.sound, p5.play, p5.capture, @p5-wrapper/react, etc.). Adding the right plugins can elevate p5.js's verdict for specific niches — e.g., **p5.brush + @p5-wrapper/react + p5.capture** is a first-class production stack for natural-brush painterly generative art.

See **[[q5.js]]** for the WebGPU-powered sibling library — drop-in API compatibility with significant performance improvement. Worth considering for priority-1 / priority-4 work when performance is the bottleneck.
